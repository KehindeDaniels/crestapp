# Design vs Backend Gaps

> Running log of mismatches between the Figma designs and the actual backend API contract (`Crest App Laravel API Collection.postman_collection (1).json`). Updated at the end of every phase. This is about **design ↔ endpoint shape mismatches** — for live implementation bugs found by testing (e.g. the CSRF/OTP issues), see `docs/bug-report-csrf-and-otp-leak.md`.

## How to read this
- **Field the API needs but the design doesn't show** → we added a form field not in Figma, always defaulted/flagged in code with a comment.
- **Field the design shows but the API doesn't use** → we render it cosmetically without wiring it to any endpoint.
- **Undocumented response shape** → the Postman collection has no example response for that endpoint, so we built against a best-effort assumption and flagged it as unverified.

## Phase 2.5 — Post-Phase-2 bugfixes (routing + skippable KYC)

Live testing after the backend's CSRF/OTP fix surfaced 3 issues — 2 real bugs, 1 new feature. Not new Figma-vs-API mismatches in the usual sense, but recorded here since two of the three touch endpoint uncertainty directly.

| Gap | Detail | What we did |
|---|---|---|
| `find-single` — CSRF is actually fixed now; hit a second, unrelated bug | First live test showed `419` (CSRF) — reported to the backend dev. After their fix, retesting showed the CSRF issue is resolved for this endpoint (confirms the fix does cover it, contrary to our first suspicion), but a NEW error surfaced: `422 { "errors": { "include_kyc": ["The include kyc field must be true or false."] } }`. Root cause: Laravel's `boolean` validation rule rejects the literal string `"true"` (which is exactly what the Postman example shows) — it only accepts real booleans or `1`/`0`/`"1"`/`"0"`. | Changed `kycApi.findSingle()` to send `include_kyc: true` (a real JSON boolean) instead of the string `"true"` copied from the Postman example. **The Postman example itself is wrong/would fail this validation if run as-is** — worth flagging back to whoever maintains the collection. Still can't confirm whether a real `kyc` status field exists in the response, since this was blocking every attempt until now — next live test should finally reveal the real response shape. |
| `find-single` self-lookup authorization unconfirmed | The only example uses `requester_id === user_id` (suggesting self-service), but there's no documentation confirming a non-admin role (tenant/landlord/etc.) is actually authorized to call this about themselves — it lives under "KYC Management" alongside clearly admin-only endpoints. | Built `kycApi.findSingle()` assuming self-lookup works; flagged as unverified. **Needs a live `curl` test with a real non-admin Bearer token** — may 403 in practice, which would mean this hook silently never resolves a real status for ordinary users. |
| `parseKycStatus()` crashed TanStack Query — CONFIRMED via live console error | Once the two bugs above were fixed, `find-single` finally succeeded — but with no `kyc` field in the response (as long suspected), `parseKycStatus()`'s designed fallback kicked in: returning `undefined`. TanStack Query forbids this — a `queryFn` resolving with `undefined` throws `"Query data cannot be undefined"` (confirmed live, `["kyc","mine"]` query key, via the Next.js dev error overlay). This is a real frontend bug we introduced, not a backend gap. | Changed `parseKycStatus()`'s fallback from `undefined` to `null` (TanStack Query allows `null` as valid data — only `undefined` is banned). `KycReminderCard`'s `status === "approved"` check is unaffected (`null !== "approved"` correctly falls through to showing the reminder). This also **finally confirms** the response truly has no usable `kyc` field — the previous two blockers (419, then 422) had prevented ever actually seeing this far. |
| `/dashboard` → `/home` rename was load-bearing, not cosmetic | `src/app/(client)/` had only `layout.tsx` — `/dashboard` didn't exist at all, so every redirect to it (proxy's guest-bounce, login's default `nextPath`, KYC completion's "Continue") 404'd. This wasn't caught until live testing because nothing in typecheck/build/lint verifies a redirect target actually has a page. | Renamed to `/home` in all 6 places it appeared (`src/proxy.ts` ×2, `login/page.tsx`, `kyc/processing/page.tsx`, 3 doc references) — backed by the real Figma "Home" frame (node `1411-2864`). "Dashboard" is now reserved exclusively for the separate admin persona (`/admin/*`, Phase 7) — this closes a gap where the *route group* was renamed to `(client)` earlier but the literal *path* still said `/dashboard`. |
| Home page created is a scoped placeholder | `src/app/(client)/home/page.tsx` was created now only to unblock the 404s above and host `KycReminderCard` — it is not the real Home screen. | Deliberately minimal (welcome heading + reminder card + a `TODO(Phase 3)` comment). Full property-feed Home screen per Figma node `1411-2864` remains genuine Phase 3 scope. |
| KYC reminder card visual design not pulled from Figma | The Home frame may already show a specific reminder-banner design; it hasn't been inspected for one. | `KycReminderCard`'s copy/styling mirrors `KycGuard`'s existing fallback CTA (same classes) rather than a pixel-accurate pull. Revisit once Phase 3 formally inspects the Home frame. |
| ~~File upload switched to Legal Documents system — real risk~~ **RESOLVED: `download_url` confirmed working** | The backend dev confirmed `/api/platform/files/upload` is dead and directed uploads to `POST /api/documents/upload` instead. The one documented Postman example showed `download_url` as `null`, raising a real risk that `kyc/submit` (which needs real URLs) would never get one. | **Live-tested and confirmed resolved**: all three uploads (front/back/selfie) returned real, usable URLs (`https://api.crestapp.ng/api/download/...`), visible directly in the `kyc/submit` request payload. `parseDocumentUrl()`'s throw-loudly design never had to fire. The stale `null` in the Postman example was misleading, not representative of real backend behavior. |
| `document_type` has no KYC-appropriate value | `/api/documents/upload` requires `document_type` from a fixed enum: `agreement, contract, disclosure, certificate, report` — a general legal-document classification system, not designed for "government ID photo" or "selfie". | Used `"certificate"` for all KYC uploads (front ID, back ID, selfie alike) as the least-bad fit. Flagged as a deliberate, arbitrary inference in code comments (`src/features/kyc/api.ts`) — worth confirming with the backend/product owner whether a better-fitting value or a new enum option should exist for KYC specifically. |
| `kyc/submit` requires an undocumented `requester_id` field | Confirmed live via `422 { "errors": { "requester_id": ["The requester id field is required."] } }` — the Postman collection's example payload for `kyc/submit` has no `requester_id` at all. Mirrors the same field on `kyc/find-single`, where it means "the authenticated user's own `user_id`" for self-submission. | Added `requester_id: ID` to `KycSubmitPayload` (`src/features/kyc/types.ts`); `src/app/(onboarding)/kyc/processing/page.tsx` now reads the current user's `user_id` from `useSessionStore` and includes it in both the initial submit and the "Try again" retry. The submit effect now depends on `userId` (not mount-only) since session hydration can resolve after the page mounts. |

## Not yet compared (future phases — flagging now, not asserting a mismatch)
These are things noticed during the initial capability check, before the relevant Figma screens were inspected in detail. Revisit when that phase starts:
- **No single `GET /properties/{id}`** — property detail is fetched via `search` with an `id` filter. Fine for now; worth double-checking the Search Property / Listing Figma screens don't assume a dedicated detail endpoint's response shape.
- **Notifications**: only mark-single-read exists — no mark-all or delete. Check if any screen implies a "mark all as read" action.
- **No saved/favorites endpoint** — check if any property card in Figma shows a heart/save icon.
- **Messaging is REST-only, no websocket** — if the messaging screens imply live typing indicators/online presence, that's a gap (would need polling instead).
- **Admin Dashboard** (separate Figma page, Phase 7) — not inspected screen-by-screen yet; expect gaps once it is (see `docs/frontend-blueprint.md` §17 for what's already known to be missing on the backend: user suspend/activate, non-KYC user directory, admin support desk, single stats-overview endpoint).
