# Design vs Backend Gaps

> Running log of mismatches between the Figma designs and the actual backend API contract (`Crest App Laravel API Collection.postman_collection (1).json`). Updated at the end of every phase. This is about **design ↔ endpoint shape mismatches** — for live implementation bugs found by testing (e.g. the CSRF/OTP issues), see `docs/bug-report-csrf-and-otp-leak.md`.

## How to read this
- **Field the API needs but the design doesn't show** → we added a form field not in Figma, always defaulted/flagged in code with a comment.
- **Field the design shows but the API doesn't use** → we render it cosmetically without wiring it to any endpoint.
- **Undocumented response shape** → the Postman collection has no example response for that endpoint, so we built against a best-effort assumption and flagged it as unverified.

## Phase 3 — KYC processing gate bug (found via a live test, real `kyc_id` created)

A live test finally exercised the full submit path end-to-end for the first time — `POST /api/kyc/submit` returned `201` with a real `kyc_submission` object (`kyc_id: 7`, `status: "pending"`), the first confirmed-working submission all session. But the UI stayed stuck on "Hold still, we are processing" indefinitely, and a **second** `kyc/submit` call then came back `400`.

| Bug | Root cause | Fix |
|---|---|---|
| Processing page's success UI never showed, despite the request succeeding | `(onboarding)/kyc/layout.tsx` wrapped **all** of `/kyc/*`, including `/kyc/processing` — the page that actually creates the "pending" status. The moment submission succeeded and `useMyKycStatus()`'s query refetched (TanStack Query's default `refetchOnWindowFocus` — plausibly triggered by switching focus to DevTools mid-test) and picked up the new `"pending"` status, the layout swapped `{children}` out for its own "Verification in progress" screen — unmounting `KycProcessingPage` mid-render, mutation state and all. The "block re-entry" gate was gating the one screen that's *supposed* to be visible right after a successful submission. | Restructured routing: moved the gated screens (`/kyc`, `/kyc/id`, `/kyc/selfie`) into a new `(onboarding)/kyc/(wizard)/` route group with its own `layout.tsx` (the same gate logic, scope narrowed). `/kyc/processing` now sits as a sibling outside that group — same URL (`(wizard)` is invisible in the path), no longer gated. Confirmed via `pnpm build`: route list unchanged (`/kyc`, `/kyc/id`, `/kyc/selfie`, `/kyc/processing` all still present). |
| Second submit attempt, 400 | Direct consequence of the bug above: once the layout unmounted the processing page, navigating back to `/kyc/processing` remounted it fresh — a new `hasSubmitted` ref (`false`) — so its effect fired `submitKyc.mutate()` again, hitting the now-real "already have a pending submission" rejection. | Resolved by the same routing fix — the processing page is no longer at risk of being unmounted mid-flight by its own layout, so `hasSubmitted` correctly persists for the page's actual lifetime. |
| `KycReminderCard` could show stale "not verified" for up to 60s after a real submission | `useMyKycStatus()` has `staleTime: 60_000` and nothing invalidated it on a successful submit — it would only pick up the new status on its next natural refetch. | `useSubmitKyc()` now calls `queryClient.invalidateQueries({ queryKey: queryKeys.kyc.mine })` in `onSuccess` (`src/features/kyc/hooks.ts`). Independent fix, not what caused the two bugs above (those were about the gate wrapping the wrong page, not about staleness), but a real rough edge worth closing while in this code. |
| Front/back/selfie image URLs echoed back as bare numbers (`"96"`, `"97"`, `"98"`), not URLs | Unconfirmed which side is at fault: either `POST /api/documents/upload`'s `download_url` field is now returning something that isn't a URL (possible backend regression — earlier session testing confirmed real `https://api.crestapp.ng/api/download/...` values), or `kyc/submit`'s response echo is unreliable and shouldn't be read literally. `parseDocumentUrl()` previously only checked truthiness, not shape, so a bare `"96"` would silently pass through as if it were a real URL. | Hardened `parseDocumentUrl()` (`src/features/kyc/api.ts`) to also validate the value looks like an absolute `http(s)` URL, throwing loudly with the actual value in the error message otherwise — converts a silent pass-through into an immediate, diagnosable failure. **Still needs a live check**: inspect the raw `POST /api/documents/upload` response body directly (not `kyc/submit`'s echo) to confirm whether `data.download_url` itself is really `"96"` or a full URL — that determines whether this is a backend regression to report or a `kyc/submit`-response quirk to ignore. |

### Follow-up: the routing fix above was necessary but not sufficient
A subsequent live test (a genuine `400`, not the duplicate-submission case) showed the exact same symptom again: request completed in the Network tab, no corresponding UI. **The routing fix's claim that `hasSubmitted` "correctly persists for the page's actual lifetime" was wrong** — it only closed the one unmount trigger already identified (`KycLayout` wrapping the wrong page). At least one other trigger exists that can unmount `KycProcessingPage` mid-request — `(onboarding)/layout.tsx`'s `AuthGuard` re-evaluates `useAuth()` on every render, and if `isLoading`/`isAuthenticated` ever flips transiently (e.g. during a background `/api/user` refetch), it renders `null`, unmounting everything below it, including a component with an in-flight mutation. A full audit of every possible unmount trigger wasn't worth chasing individually — the underlying fragility is architectural: **a network request's outcome was only ever recoverable through the specific component instance that fired it.**

**Real fix**: moved submission state (`submissionStatus: "idle" | "submitting" | "success" | "error"`, `submissionError`) into `useKycWizardStore` (`src/features/kyc/wizard-store.ts`) instead of relying on `useSubmitKyc()`'s local, component-scoped `isPending`/`isSuccess`/`isError`. The mutation's own `onSuccess`/`onError` callbacks write the outcome directly into the store — since a Zustand store lives outside the React tree, this happens regardless of whether the component that called `.mutate()` is still mounted by the time the response arrives. `kyc/processing/page.tsx` now renders purely from `wizard.submissionStatus`, so even a fresh remount (for any reason, known or not-yet-discovered) shows the correct final state instead of a stuck spinner. This is a more durable fix than chasing individual unmount triggers one at a time.

### Architecture note: view-model / mapping layer (explicit instruction, not a default pattern used elsewhere yet)
Per explicit instruction, Home is built around view models rather than binding components directly to raw API responses — e.g. `PropertyCardModel` (`src/features/properties/models.ts`), `ProfileViewModel` (`src/features/profile/models.ts`). `toPropertyCardModel()`/`toProfileViewModel()` are the only places that touch the raw response shape (string prices, relative media paths, nested `owner.profile.*`, etc.) — every component downstream binds to the clean model. A backend response-shape change only requires updating the mapper, not every component that renders a card. This is a deliberate deviation from earlier phases (auth/KYC hooks return raw-ish parsed data directly) — not retrofitted onto them, but worth applying to future features that render lists of backend objects.

Please submit your KYC documents.", "error": "KYC_NOT_VERIFIED", "required_documents": {...}}`. `MakeOfferDialog` was showing a generic "Couldn't create this offer — try again" for this. | `ApiError` now captures `error` (not just `error_code`) as `.code`, plus the full raw body as `.details`. `MakeOfferDialog` special-cases `code === "KYC_NOT_VERIFIED"` with a specific message and a link to `/kyc`; any other failure now shows the real backend message instead of a generic string. Confirms this is intentional backend behavior — a real-estate escrow platform requiring identity verification before a binding offer is a reasonable business rule, not a bug. |

### Architecture notes
- **`PaymentLinkInfo`** (new, narrow type: `paymentLink`/`paymentGateway`/`paymentExpiresAt`) replaces using the full `OfferModel` as the payment-session cache value — needed so `useRegeneratePaymentLink` can always write a complete, valid cache entry on its own, with no prior `OfferModel` required to merge into. Everything else the offer page renders now comes from `ContractStatusModel` (real, re-fetchable), which gained its own `totalAmountFormatted` so the Order Summary no longer depends on the one-time cache at all.

**Verified:** `pnpm typecheck`, `pnpm lint`, `pnpm build` — all clean, still 30 routes.

**Follow-up UX question:** since "Continue" opens a new tab and stays clickable, repeat clicks would keep spawning tabs. Not a data/financial bug — every click hits the same cached `payment_link`/`gateway_reference`, not a fresh `quick-create`, so there's no risk of duplicate contracts or double charges — but still worth tightening. `PayButton` now relabels to "Reopen Payment Page" after the first click and briefly disables itself (2s) right after each click, purely to stop rapid repeat-clicks from opening several tabs at once. Deliberately a debounce, not a one-time lock — reopening after accidentally closing the tab is the exact case this button exists for.

## Phase 11.8 — History's per-tab empty state, and a missed cache invalidation on cancel

Two more from live testing: switching to the Completed/Cancelled tabs when they happened to have zero matches collapsed the *entire* History page (tabs, search, table and all) into the full-page onboarding empty state; and cancelling an offer wasn't reflected in History afterward.

| Finding | Detail | What we did |
|---|---|---|
| **Per-tab empty state showed the wrong (full-page) empty state** | `hasAnyTransactions` was computed from `data.summary.total_transactions` — but `data` itself is fetched *with the active tab's `status` filter already applied server-side* for Completed/Cancelled. So that summary reflects "how many match this tab," not "does this user have any activity at all." Clicking a tab with zero matches wrongly triggered the same big "No activities yet" screen meant for genuinely brand-new users. | Only the unfiltered **"All"** tab's summary is trusted as a real "any activity ever" signal now (`hasAnyTransactions = tab !== "all" || ...`). Every other tab's zero-match case falls through to the existing, smaller inline "No transactions match these filters" message instead — tabs and search stay visible. |
| **Cancelling an offer didn't update History** | `useCancelOffer` invalidated the contract's own cache, but History's transaction list lives on a completely separate query (`queryKeys.transactions.*`) that was never told to refetch. | Added `queryClient.invalidateQueries({ queryKey: queryKeys.transactions.all })` to `useCancelOffer`'s `onSuccess`. **Still open, not yet confirmed:** whether the backend actually updates the linked *transaction's* own `status` to `cancelled` when a *contract* is cancelled — the confirmed `Cancel Contract` response only shows the contract object changing, with no transaction object in it at all. If a cancelled offer still doesn't show under History's Cancelled tab after this fix, that would point to a real backend gap (transaction status not cascading from contract cancellation) rather than a frontend caching issue. |

**Verified:** `pnpm typecheck`, `pnpm lint`, `pnpm build` — all clean, still 30 routes.

The confirmed `PUT /api/notifications/preferences` body is just 3 plain booleans: `email_notifications`/`sms_notifications`/`push_notifications`. ### Architecture notes
- **`useFullProfile()` and `useProfile()` (topbar) now share one base query** (`useProfileSelect`, one real `GET /api/profile` fetch under `queryKeys.profile.detail`, each hook applying its own `select`) — the same shared-query-plus-`select` pattern already fixed a real cache-corruption bug in Notifications (Phase 9); built this one correctly from the start instead of repeating that mistake.
- **Three dialogs (Edit Profile, Payment Method, Notifications) needed to reset their pre-filled form state each time they reopen** — normally a `useEffect` job, but this repo's lint config (`react-hooks/set-state-in-effect`) disallows calling `setState` synchronously inside an effect. Fixed with React's documented alternative: a `key` on each dialog, bumped only in the button `onClick` that opens it (never on close), forcing a fresh remount whose `useState` initializers re-read current props/query data — no effect involved. The Notifications dialog went a step further and dropped local draft state entirely, since a query's async data can't safely seed a `useState` initializer on a fresh mount anyway; each toggle now saves immediately instead of batching into a Save button.
- **New `MyPropertiesParams`/`useMyProperties()`** in the `properties` feature (not `profile`) — property data belongs there, matching how the rest of the app is organized; `queryKeys.properties.mine` already existed, scaffolded but unused until now.
- **`nav-config.ts`'s Profile item flipped to `enabled: true`** — the last remaining disabled top-level nav item.

**Verified:** `pnpm typecheck`, `pnpm lint`, `pnpm build` — all clean, 32 routes (added `/profile`, `/profile/listings`).

## Phase 13 — Shortlets (+ self-service role switch)

New feature area, from the 2026-07-22 Postman collection (15 new endpoints, all with full real saved examples — unusually well-documented) and `Shortlet_Frontend_UI_UX_BRD.md`. Blueprint written first in `docs/design/shortlet-implementation-plan.md`; this section records what was actually built and the gaps that remain. A shortlet listing is a real `property` record with a third `purpose` value (`shortlet`), plus a booking system (rooms → search → quote → hold → pay → auto-confirm, no checkout).

**New this phase, and relevant beyond shortlets:** `PUT /api/profile/role` — a genuine self-service role switch (in the User Profile folder, not shortlet-specific). This is the endpoint the earlier role-consolidation discussion assumed didn't exist. Wired into Profile as a "Switch account role" dialog offering the four consumer roles (buyer/tenant/landlord/seller); updates the session store + role cookie so gates (List Property's `canList`) and proxy redirects reflect it without a re-login.

| Gap | Detail | What we did |
|---|---|---|
| **No owner-facing bookings endpoint** | The BRD plans an "Owner bookings" screen, but only `GET /bookings/mine` (guest) and `GET /admin/shortlets/bookings` (admin-only) exist. | **Not built.** Owner management covers listings + room calendars only; incoming-bookings visibility is deferred until a real owner endpoint exists. Flagged as the top open question to backend. |
| **Role naming is a relabel, not a new enum** | BRD says "Shortlet owner"/"Shortlet user"; the actual role enum is unchanged (`landlord/tenant/seller/buyer/lawyer/surveyor`), and `Switch Role`'s example switches to `"landlord"`. | Built the switch around the real existing roles, with copy noting capability (a host switches to Landlord). **Which roles may switch, and which one shortlet-creation actually requires, is unconfirmed** — the UI surfaces the real backend error (e.g. 403) verbatim rather than pre-gating. |
| **No single-booking `GET` endpoint** | Only list endpoints exist for bookings — no `GET /bookings/{id}`. | The booking detail page reads from the polled `/bookings/mine` list and finds the row by id. Polling (15s) means it flips `pending_payment`→`confirmed` on its own after the webhook; workable, but flagged to backend as a likely oversight. |
| **Only Flutterwave** | `Pay Booking`'s only example uses `gateway: "flutterwave"`. | Single real "Pay with Flutterwave" action (reuses Offers' new-tab redirect + cache-only payment-session pattern), not a gateway picker. Same treatment as Make an Offer. |
| **`Switch Role` has no saved response** | Body confirmed (`{role}`), response shape unknown. | Trust the role we sent, not a parsed response — `useSwitchRole` sets the session role from the mutation variable on success. |
| **Money typed inconsistently across responses** | Some fields are decimal strings (`"40000.00"`), others plain numbers (quote's `subtotal: 80000`). | `models.ts` coerces everything through one `num()` helper; components only ever see formatted strings. |
| **Nested `rooms`/`property` trimmed differently per endpoint** | Create returns the fullest room shape; list/browse/search return only `status/room_id/name`. | Optional fields on `ApiShortletRoom`/`ApiShortletListing` reflect "not always in the example," and the models fall back gracefully (e.g. `capacity ?? null`). |
| **Photos** | Not yet wired for shortlets. | Listing cards/detail show a neutral placeholder. The create response returns a real `property_id`, so the existing `propertiesApi.uploadMedia` flow can be reused later — deferred, not blocked. |

### Architecture notes
- **New `src/features/shortlets/`** — full `types/api/models/hooks/index`, same structure as every feature. Deliberately mirrors `offers` for the pay flow: a cache-only `paymentSession` key (seeded by `usePayBooking`) kept strictly separate from any re-fetchable query, exactly the split that avoided the Notifications-style cache-corruption bug (Phase 9).
- **New `shortlets` query-key namespace** with factory functions, matching the `properties`/`contracts` convention.
- **Session store gained `setRole`** + a narrow `persistRole` in `token.ts` (updates only the role cookie, leaving token/status untouched) — so a role switch doesn't require a full re-login to keep proxy redirects consistent.
- **7 new routes**: `/shortlets` (guest search), `/shortlets/[listingId]` (detail + availability + quote + book), `/shortlets/bookings` (my bookings), `/shortlets/bookings/[bookingId]` (booking detail + pay + cancel), `/shortlets/manage` (owner listings), `/shortlets/manage/[listingId]` (activate + rooms), `/shortlets/manage/[listingId]/rooms/[roomId]` (calendar). One new nav item ("Shortlets"); owner + bookings reachable via buttons on the search page, keeping nav uncluttered per BRD §2.

**Verified:** `pnpm typecheck`, `pnpm lint`, `pnpm build` — all clean, 35 routes. **Not yet done (same caveats as Offers, Phase 11):** no live end-to-end test through a real Flutterwave payment to confirm the `pending_payment`→`confirmed` transition; no live confirmation of which role the backend requires for shortlet creation (Gap 2); photo upload deferred.
